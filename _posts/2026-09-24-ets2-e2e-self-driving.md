在离开前公司后我被竞业。
我觉得我的工作经历里，大部分都是完成某个需求。
这些工作脱离了原来的语境根本没有明显意义，
我也很难跟面试官说明白我到底做了什么。
我希望在这段时间里做一个相对完整的项目。

# 录制尽可能完整的数据

我需要自己录制欧卡模拟器驾驶数据来制作数据集。我的数据来源有两个:

1. 游戏截屏，按照 10 Hz 的频率获取。
2. 遥测插件获取的数据。它是一块 4KB 左右的 telemetry byte buffer。

在我做的第一个版本数据集中，我犯了严重的错误 ------
为了减少录制数据的体积，我直接解包了 telemetry 并只留下了我认为重要的字段。
因为当时我认为我只需要自车的位姿、速度、油门刹车、方向盘转角就足够了。
即使实际的自动驾驶的核心标量输入就只有这些，这么做很快就会遇到问题：

- 需求会增加。
  录制时认为不重要的信息，后续可能要用来
  筛选数据、
  标定相机、
  区分左右舵等。
  录制丢掉的数据无法重新补录。
- 处理代码可能出错。
  提前解包报文，如果解码代码写错无法修复历史数据------并且事实上我就写错过。

核心原因是重新录制的代价很高。

最后我的选择是将游戏截图 resize 到 1k, 然后压缩为 mp4; 遥测数据压缩为 zstd。
我希望在录制数据阶段，尽可能避免任何可能出错的环节。

# 在编写任何代码前先考虑交付产物

在编写任何代码前考虑好有哪些交付物。
由交付物的定义决定模型功能，并自然地切分出模块。
我认为的交付物通常有：

- artifact：一组具有某种 schema 的文件。比如 checkpoint, 数据集等。
- IPC 接口。比如 http server。

我觉得直接交付代码作为 lib 依赖对于快速开发的个人项目是严重的陷阱。
对于快速开发的项目，应该尽可能使得各个部分完全隔离代码，
仅通过不依赖代码的 schema 进行协调。

我会根据我要使用的库或者服务，通过满足它们的使用要求反向设计我的交付产物。
这些第三方接口相比我自己的代码经受了更多人的检验。
以数据集为例：

首先我要在 hf 上托管我的数据集
（现在让原始录制数据集尽可能完整且减少操作的理由又多了一个）。
我希望尽可能不要重传数据集，且添加数据可以直接添加文件。
WebDataset 是最适合的格式，我只需要按照文件大小限制，
把全部 bag 打包为若干个 tar，上传到 hf 即可。

然后考虑训练使用的数据集。
它只在本地，可以承受一定的重建代价。
因此我会解码全部数据，并根据需要进行剪裁------
图像剪裁并缩放到需要的大小，telemetry 解码然后只保留需要的列。
只做上述优化并不能跑满 GPU，
现在的瓶颈是 IO------解包后的小文件过多。
我需要根据时序重新组织小文件以方便 mmap。
在经过一些尝试后我最后打算用 Arrow dataset 解决这个问题。
假如自己维护这个功能，会需要自己面对很多工程细节，并且很难拓展字段类型。
所以第二个阶段的产物是单帧的 Arrow dataset。
在这个阶段还会进行一些比较重的单帧预处理，
比如用 yolo 检测图像中其他车辆、
查找每帧的位置处于 ets2 的哪种 prefab。

最后，
在训练时将 Arrow dataset 
展开为每个窗口一个 sample 的 pytorch dataset。

# 如何用 Agent 编写全部代码

在这个项目里，我几乎用 agent 编写全部代码。并且很少 review 代码。
在 agent 话题中，流传的技巧很多，但实际有用的很少。

我认为在长期上大概率没用的：

- 用 AI review AI，或者指望 agent 重构来优化实现模式或者局部设计。
  失败原因是偏好对齐。
  人与人之间对齐偏好只用较少的沟通，
  而人和 AI 对齐偏好是极其困难的。
- 指望 agent 生成的记忆或者 agent 生成的注释让 agent 更理解项目。
  失败原因是幻觉。
  记忆、注释之类，在进入下一个 session 会变成缺失上下文的权威引用。
- 强制 agent 按照非常见轨迹执行的 skill，我不认为它们会有用。
  失败的原因是很可能不符合训练分布。
  大模型公司会在自己的 harness 上做 RL，
  这是 LLM agent 能力提升的重要来源。
  而 skill 干预产生的轨迹可能在训练分布边缘。

我认为有效的方法有两个。

第一个做法是通过硬边界分割项目为多个 repo。
多个 repo 之间只通过约定好的接口协作，不引用对方的代码。
这么做有几个好处：

- 接口即功能范围。
  开发前我被迫需要设计好这个 repo 的功能范围，
  而不是交由 agent 自由发挥。
- 差的接口设计会很快暴露，而不是被 agent 的代码生成能力掩盖。
- 将每个模块的复杂性限制在较低的程度，方便随时重写。

在这个项目里，我进行了很多次重写。
我认为在用 agent 接管全部代码后，
想要完全避免 agent 把代码库写到不可维护是不现实的。
必须接受在用 agent 接管代码库后会导致的频繁重写。
我们可以做的是及早发现及早重写，以及控制每次重写的范围。

第二个做法用于生成具有某个特定功能的代码。
我使用以下三步流程来生成一个完整功能的提交：

1. 在 agent 无法访问代码的环境（比如网页端）进行通用方案的询问
2. 在 agent 中尝试实现需求，记录需求被逐步澄清的过程。
   直到自己认为对这个需求完全理解。然后回退所有改动。
3. 手写一份 prompt, 让 agent 一次性生成全部改动------无人类介入。
   遇到任何必须人类纠正的问题，
   都需要先 clear agent session 并清空代码，
   再根据失败原因修改 prompt 重新让 agent 执行。

在我的三个步骤中，
只有第二步在将 LLM 当作人类对话（因此第二步的结果需要真实的人类来整理）。
第一步我希望 agent 只通过训练知识（以及可能 WebSearch）来给出方案，
避免将先前生成的代码当作权威引用。
第三步我在尽可能对齐 benchmark 使用 agent 的方式。

我认为将 LLM 当作人类、或者同事是错误的使用方式，
即使它有很多地方表现的类似人类。

# 闭环验收比其他看起来重要的问题都重要

在我第一次在游戏里让车跑起来之前，
我尝试对模型做了很多次优化。
我一开始的想法是，在实际在游戏里运行前，让 loss 尽可能降低。
但我实际在游戏里测试后，我才意识到我之前在浪费时间。

第一点，把闭环跑通了才能真正 triage 问题。
在我第一次闭环测试的时候，
我的控制器是让 agent 直接实现的 pure pursuit，
并且我没有调参数。
在实测里，这个版本的闭环表现是一直撞路沿。
当时我怀疑的是模型训练坏了。
我认为模型只是在 copycat 输入状态 ------
这其实是带着锤子找钉子。
我知道自动驾驶模型很可能会出现这种问题，
但这不代表类似表现的问题一定都是这个 root cause。
在我重新训练了几个版本之后没有任何优化，
我才回想到我没有调过 pure pursuit 参数。
实际上我修改并重训的几个版本相比第一版没有明显进步，
我只是在修复我自己幻想出来的问题。
在实际闭环验收有基本正常的表现前，做的任何分析都是带有很大程度猜测的。

第二点，闭环评估的体验是兜底的评价指标。
在欧卡自动驾驶这个任务中，其实 val loss 几乎不反应闭环的表现。
以及基于开环 rollout 的指标可能比 loss 好但也不等于闭环体验。
没有闭环评估根本无法确认一个改动是否真的有效。

第三点，从训练模型到实际部署可能有额外的 trade off。
pure pursuit 追踪路点对我来说还是过于复杂。
我最终选择了让模型输出每个时间点上的速度和角速度。
这个输出可以转换为路点（假设车辆不侧滑、忽略挂车），
但对我的场景更容易闭环控制。
尽早做闭环验收，可以及早发现这个问题，及早重构代码。

# 总结

这篇文章里我提了很多主观观点。
但我认为绝大多数都和常识相符。
我觉得这段经历我最大的收获是重新构建了我的工程常识。
