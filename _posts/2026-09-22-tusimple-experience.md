我的唯一一份实习和第一份正式工作都在 TuSimple。
两段工作分别是 intern —— 从 22 年 7 月到 22 年 11 月，
以及 fulltime —— 从 23 年 7 月到 24 年 3 月，

这期间我做的都是地图相关的项目，主要是地图编译和地图 SDK。

# 延迟优化——砍掉没被用到的通用性

在实习期间我做的第一个 feature 
是为地图 SDK 优化一个批量曲率查询接口。
这个接口只有 planning 使用。
可以认为在一条离散曲线 $$C: x = x(s), y = y(s), 0 \le s \le l$$ 上，
计算所有查询点 $$(x_i, y_i)$$ 在曲线上最近点处的曲率。

在地图 SDK 中，几乎所有查询接口都额外编写了一个批量版本。
但大多数批量接口，被提供的目的只是消除在 python 中使用时的循环。
这些批量接口只是在循环调用单点查询。

旧版本的批量曲率查询也是如此，它也做了上述的通用优化。
但总之它并没有达到 planning 的延迟要求。

对于单点查询来说。
做法是在曲线上二分 $$s_0$$, 找到最近的 $$(x(s), y(s))$$, 然后计算曲率（假设曲线总是足够平滑）。

对于批量查询而言，假如输入是完全随机的，那么当前直接循环调用单点查询就是最好做法。
但是假如能够保证输入点 $$(x_i, y_i)$$ 所对应的 $$s_i$$ 递增，
我就不需要每次都二分。可以双指针扫描，我不想在这里展开这个基础算法，但结果是复杂度可以从 O(m log n) 降低为 O(n+m)。

planning 的查询，事实上的投影距离 $$s_i$$ 就是递增。
这是因为 planning 需要查询的是 route 上的曲率，并且 route 在 refline 上的投影不会后退。

因此，SDK 不需要为不存在的查询组合埋单，可以在复杂度上优化这个接口。

# 延迟优化——利用先验知识

正式入职后，我做的第一个比较完整的 feature 是为感知提供可行驶区域的 grid map。
它原本是感知组自己维护的一层 Map SDK adapter，
我做的工作是将它迁移进 map SDK 并继续维护。
它的主要功能是产出 grid map，用于表示自车附近的可行驶区域。

我了解到他们需要这种表达形式的核心需求是，
对于“点是否落在可行驶区域”这类查询， map 提供的接口太慢了。
另外，他们可以通过 grid map 化的方式将可行驶区域作为 feature （可能是作为神经网络输入）。

map SDK 在做 “点是否落在可行驶区域” 这类基本查询时的代码并没有明显问题。
对于一个一般性的点是否落在目标区域点问题，
做法肯定类似于用 RTree/KDTree 等数据结构，
先找到所有可能存在覆盖的几何图形，然后逐个判断是否真正覆盖。

但这并没有真正和感知对齐需求，
1. 他们其实不需要那么高的精度。我们在做几何覆盖时没有做任何近似化处理。
2. 他们需要在非常有限的区域内，做密集查询，而不是在整个地图上随机查询。

所以我们可以低频地处理自车附近固定范围内，代表可行驶区域覆盖的 grid map。
然后提供 O(1) 复杂度的“点是否落在可行驶区域” 查询能力，以支持高频查询。

后来 Planning 也有关于 “可行驶区域” 类似信息的需求。
他们需要的信息形式和感知不同。
他们需要知道在 route refline 上，每个点到两侧路沿的距离。
且 Planning 有很严格的延迟要求，需要在毫秒级内完成前方数千个采样点的查询。

Planning 只会查询自车附近区域的点。因此我在 map SDK 中还是可以利用类似的先验进行优化。

在自车位置更新一段距离后，异步计算 route 上每一个点的答案。
在高频查询时 O(1) 返回。

具体如何计算两边距离？我的做法是通过可行驶地图元素的公共边，不断向外拓展可行驶区域。
限制纵向拓展距离。
这样可以得到封闭的可行驶区域。然后问题转换为在封闭区域内的一条离散曲线，计算曲线上每个采样点到区域两边的距离。

在自动驾驶的语境下，
下游需要的往往都是具有很高相关性的密集查询，
并且精度上也很可能存在很大让步空间。
优化方法往往并不是在一个 general 接口上挤延迟，
而是根据先验的热点先进行预处理，然后快速回答全部的相似查询。

# 系统设计——只有硬边界才被人尊重

我在 TuSimple 维护了旧地图编译工具（下文称 Map Builder），
并参与了新地图量产微服务产线的开发——
我的主要工作是把地图编译工具的对应功能拆分并迁移为服务。

Map Builder 是一个复杂的单体程序。
具体来说，它的输入是矢量化建图的结果，输出是 Map SDK 需要的结构化语义地图。
复杂的流程和相对模糊的验收标准，很容易导致难以维护的代码——Map Builder 也不例外。

Hyrum 定律: 任何可观察行为都会被依赖，包括你没打算承诺的行为。这一点在 Map Builder 这类软件中体现的非常明显。

现在假设你要从 0 开始实现一个从矢量化地图到语义地图到转换工具。
大概率你会先设计一个目标数据结构，它几乎和 Map SDK 的结构对齐。
然后你将这个构建分解为几个流程，每个流程一个函数。
每个函数输入目标数据结构引用，职责是往目标数据结构里填数据。
这基本上就是最简单的做法。

所以你就打下了一个很差的基础：

- 所有模块的输入输出都是那一套数据结构。
  但模块间执行顺序所形成的事实规范被隐藏起来了。
  且没有人能够为此写文档。
- 极其容易在不同模块间错误的共享代码。这些错误共享代码会逐渐变成不可被修改的遗留代码。
- 理解整个 repo 很难，但快速 hack 出自己想要的结果很容易。

Map Builder 的状态正是如此。
首先代码库里会看到一堆的 Legacy 函数。
读代码会发现很多函数的前置条件依赖其他代码的实现细节，而不是接口（或者至少应该有文档）。
实际开发中相当多的修复都只能在补丁上叠加补丁。
好消息是 Map Builder 只需要支持固定的路线！
所以补丁是可以被穷尽的，只要我们把所有问题当作 corner case 并不停往上叠补丁。

微服务架构可以很大程度改善这些问题：

- 只有序列化过的东西才能被依赖。
  模块间必须通过 IPC 交换数据，Hyrum 定律的作用面从“整个实现”缩小到“schema里写出来的字段”。
- 每个服务有名字、有 owner。即使都是一个人开发，两个服务也需要两次不同的 commit。
  沟通边界决定了代码边界。
- 开发者不需要完全理解其他人的服务，也更难让其他服务配合自己 hack。

在 TuSimple 工作时我并没有理解以上的好处，我一直觉得跟产品经理反复沟通很麻烦。
反而在 Map Builder 中我只要能交付功能就行，其他都不用管。

我在大量使用 LLM Agent 进行编程后才理解到微服务架构的好处。
LLM 永远都更倾向于直接 hack 你的架构来实现功能，
除非你的架构有让它不得不尊重的硬边界。

# 一些浮点数处理经验

我被要求修复一些由浮点数判断导致的 Map Builder bug。
它们可能表现为，同一个位置出现重复点、曲线相交没有正确断开，等等。

在 Map Builder 中散落了很多浮点数相等判断，
它们中一些没有带 eps 直接比较二进制相等，
其他带了 eps 但可能每处使用的 eps 不同。
并且，基于 eps 的相等判断不具备传递性，即使 eps 进行统一处理也还是可能出现 bug。

我的做法是对于输入的数据先做了浮点数量化。
我不太确定当时怎么做的了，印象里甚至有点复杂。
但实际上根据固定的精度直接截断就足够了，或者标准化为 
$$n \times \mathit{step}_{\text{precision}}$$。

并且在通过计算产生新点后需要对新点进行量化。在 Map Builder 中只有两种情况：

1. 对离散曲线重采样
2. 两条曲线相交计算交点

这两种情况都只会做非常有限的次数，因此不会累积误差。

在所有点被量化后，浮点比较会很容易。我们当作非浮点数做即可。
且对于可能使用了 eps 的几何库，只要量化的 step 超过 eps, 也不会出现问题。

# 修复一个 fcntl 导致的问题

我修复了一个由 fcntl 导致的多进程多线程程序抛出死锁避免错误的问题。

Map SDK 在特定情况下会抛出 "Resource deadlock avoided"：

- 两个不同的进程持有 Map SDK —— 可能是两个不相互通信的算法模块
- 一个按照 A, B 的顺序加载地图块
- 另一个按照 B, A 的顺序加载地图块

这个问题以前一直没有出现，因为正常情况下，所有进程都只对自车附近的地图块做查询，所以地图块总是按照固定的顺序加载。

Map SDK 对于打开的地图块，需要写入缓存。因此需要通过基于 fcntl 的文件锁进行进程通信。
而 fcntl 的锁粒度是进程级别。当 

- P1T1 先获取 A 的写锁
- P1T2 尝试获取 B 的读锁
- P2T1 先获取 B 的写锁
- P2T2 尝试获取 A 的读锁

包装 fcntl 的 Boost interprocess_exception 会抛出错误，
即使在考虑了线程模型后这并不存在死锁。
因为在 fcntl 的视角中只有 P1 P2 在获取锁。
这似乎是一个遗留问题，因为 fcntl 是在没有线程的时代实现的。
一个修复办法是在捕获到抛出的错误后就等待一段时间。

当时写了最小实现可以复现这个 bug, 但我理解不了为什么会报错。
最后在一篇博客上发现了解决办法：
https://mxcao.me/posts/debug-resource-deadlock-avoided/
