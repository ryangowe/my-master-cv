在离开 TuSimple 后几个月，我加入了另一家自动驾驶公司。
这段经历从 24 年六月到 26 年五月，
大约两年。主要做感知融合。

对比在 TuSimple 的经历，在这家公司做的事情更加下游。
虽然感知相比地图是更加核心的模块——L2 方案通常也不依赖高精地图——
但具体到融合这一层，工作内容主要是在模型输出之后做处理。
我时常感觉做的事情很多，但能讲出来的有意思的经历很少。
相当多工作内容都可以用“给模型兜底”来概括。

# AEB 感知融合

这段经历的大多数时间我都在做 AEB，直到离职。

我做 AEB 融合的整体思路如下

1. 前提：用状态向量表达所有障碍物
1. 对所有上游检测结果 D，根据先验设置量测噪声
1. 根据运动学公式外推融合结果 F 的估计，对齐到检测 D 的时间戳
1. 用马氏距离计算 D 和 F 的匹配代价，进行二分图匹配。
   子集 Dm 和 Fm 一一匹配。Du, Fu 是未匹配部分。
1. 逐个用 Dm 中的元素更新 Fm。用 Du 中的元素创建新融合结果。
1. 根据一些规则对 F 中的元素退役。

这个差不多是我写的第一个版本。
接下来做的就是根据实际触发情况人肉反向优化，除了调整量测噪声等参数外，还需要做大量规则：

- 我会根据距离以及 yaw 角设置线性变化的量测噪声。
  但特定模型输入在部分区域的检测明显更差，需要单独挖区域处理。
- 二分图匹配中，马氏距离只是最后区分手段。仍然需要大量规则进行提前过滤。
- 类型标签无法用状态向量表达，只能全程外挂处理。
- 更新历史可能反过来影响量测噪声——假如某路输入误差很大，且没有速度估计，那么不缩小量测噪声根本更新不动结果。
- 插入各种规则防止状态向量被更新出不合理的运动轨迹。
  尝试利用障碍物位置关系、障碍物和车道线间的位置关系的先验，约束运动轨迹。

即使需要大量后续规则才能让 AEB 工作，但我还是认为这个模块是可以设计好的。
我认为在开发过程中犯了一些错误：

- 错误的引入 tracker 的抽象。把各种算法封装为围绕 tracker 的操作。
  这引入了 tracker 是整个系统中心的幻觉，打了一个不好的基础。
- tracker 承担了过多的职责，一些合理需求长期作为 hack 存在没有被分离。
  比如场景识别完全应该是独立的任务。

回头看，一些本可以抽象为子模块的规则散落在各个地方，
而在交付压力下，修改更多是手术刀式的局部修复，而不是回头修正早期的参数设定。

# LiDAR 后处理

我为 L2 的 LiDAR freespace 检测做了后处理模块（freespace 实际上指的是障碍物点）。

最开始是一个过滤雨天 LiDAR blooming 的需求。
LiDAR 的激光光束也存在一定发散角。
对于高反射路牌覆盖角度之外的相邻角度，
有角度偏差的弱光束蹭到高反射物体也能够形成足够强的回波。
因此 LiDAR 对于高反射物体的检测存在膨胀现象。
在雨天的场景，LiDAR 窗口以及空气中的水滴会让光束散射，导致膨胀更加严重。
这可能导致错误的自动刹车。
我的做法是聚类高反射点，对每个簇做 PCA 来拟合路牌所在的平面，然后消除周围膨胀的误检。
并可以通过视觉结果补充被删除区域的 freespace 检测。

后续我接到为 freespace 检测增加记忆功能的需求。
当传感器覆盖存在盲区时，例如低速掉头这类场景，当前帧的检测不足以描述周围环境。

我用一个 local 坐标系的循环 2d grid map 来记录历史的 freespace 检测。
根据 grid 在 baselink 下的位置来决定更新策略：

- 一定在非盲区的 grid: 每帧清空历史，填入新的检测
- 可能盲区的 grid: 在离开非盲区前的最后 N 帧都有检测，则保留最后的历史检测

# 面向 HMI 的可视化

感知结果需要重新表达为用户可以接受的形式。
我做了 crosswalk 和 freespace 的可视化转换。

对于 crosswalk，在比较理想的情况下，感知可以给出平行于行人方向的两条线。
但可能存在错误断开、错误连接、扭曲等情况，尤其在十字路口这类 crosswalk 较多的场景。
由于对延迟要求不高，可以等到出现较为合理的检测后再产出 crosswalk 矩形；
在多帧上总是用 crosswalk 矩形去捕获附近的检测线——而非让检测线持续匹配。

对于 freespace, 我类比了布料模拟的思路，将离散障碍物点转换为用户可能关心的 curb linestring。

第一步先降采样。我以自车为中心按照角度分箱，每个角度只保留最近的 curb 点。
我会在一个近似路面的长矩形上等距取点，以这些点为依据来进行角度分箱。
这样做让道路远处两侧的采样更密。
这样做完可以得到一个粗糙的结果，可能出现的问题是部分角度取到的不是最近的 curb，这会导致采样点跳变。

第二步对左右两侧聚类，然后分别求凸包。
我借用了布料模拟的直觉。想象把一块布覆盖到一侧的障碍物点上。
如果把布拉紧会得到凸包的连线。放松后会逐渐贴紧 curb。
凸包顶点是布料一维曲线上的支撑点。

第三步做松弛。设置一个距离阈值，从某个支撑点出发。
如果距离内存在其他采样点，则认为它们位于同一 curb, 将它吸收进折线；
如果距离内不存在其他障碍物点，则认为 curb 断开，到下一个支撑点继续操作。

最后可以得到若干段最近路沿的折线，保留路沿开口，并过滤后方不关键的检测。

# 一些错误观念

我观察到一些算法工程师具有一些明显错误的工程观念。

**错误的 OOP 观念**

由于我们使用的是 monorepo, 我可以看到不少的错误 OOP 实践 。
实际上我认为 OOP 在自动驾驶中的应用面是非常窄的，甚至算法代码完全不应该写 OOP。

1. 数据的 layout 不可忽视。希望用抽象接口屏蔽底层的数据 layout 是幻觉。
2. 自动驾驶的任务性质。算法会希望获取能获取的所有数据以提升效果。提前抽象对效果可能有害。
3. OOP 容易误导开发者引入并隐藏过多的状态。实际上大多数算法只需要多帧输入，需要跨帧状态的情况极其有限。
4. OOP 不是好的复用代码方式。复用代码前，应该先将过程转换为不依赖业务需求的形式。
   否则会产生不敢改动的 legacy 代码。

我认为我们需要抛弃可以靠抽象屏蔽一些底层数据 layout 的幻觉，以及抛弃代码复用的幻觉。
承认必须要为特定的数据写特定的算法。

**错误的配置观念**

对于模型训练来说，所有的超参数都可以配置是好的。
但是对于非模型算法而言，把所有参数都一对一抽到 json 或 yaml 里是不合理的。

1. 大量参数间存在强耦合，大部分参数应该由其他参数计算得到。一比一抽配置项会得到完全无法配置的配置文件。
2. 大部分算法代码并不是为可配置而写的，而是先写死参数、调通、再把参数抽到 json。
   这导致大多数参数不存在可以调整的空间。另外交付压力也不允许开发写真正可配置的算法。

我认为对于稍微有点复杂度的模块，手写配置到实际使用的参数就必须经过一道转换程序。
以允许配置项之间解耦且具有高动态调节范围。
但实际上大多数情况下可配置只是被当作政治任务来完成。

**标签化的性能理解**

虽然我对程序性能也并没有非常深入的理解。但还是可以发现开发中遇到的不少错误的标签化理解

1. 认为引用一定比拷贝快。这么做忽略了解引用的开销，以及可能存在的指针别名阻碍读取优化。
2. 滥用 shared_ptr。实际上 99% 的接口根本不涉及所有权，根本不应该用任何智能指针。
   滥用 shared_ptr 对于 cache, 对于并行度都是有害的。
3. 尝试从函数体内返回临时变量的 const reference 再拷贝，或者尝试 return move。 
   对 RVO 完全没有了解。

# 离职

做 AEB 一开始比较有意思,但是后续主要是修复仿真误触发。
而且交付压力很大，仿真出的问题也排很高优先级。
没有从功能目标出发的正向需求。
然后做了比较长时间也没有分化每个人的职责，几个人一直挤在同一块代码里改。
感觉没有太多积累。
